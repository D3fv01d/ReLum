# ReLum 学习体系与内容规范

本文档面向课程作者和维护者，不应作为产品介绍直接展示在前端。

## 1. 产品定位

ReLum 是安装在用户本机、配合 Docker 靶场使用的网络安全学习环境。核心学习闭环为：

1. 明确路径目标和前置要求。
2. 按阶段学习专题模块。
3. 在单个模块内依次完成概念、判断、实操和防护内容。
4. 启动本地靶场完成实验。
5. 以服务端 flag 验证成功作为题目完成的唯一标准。
6. 记录证据、复盘错误并进入下一模块。

## 2. 参考平台与采用原则

### PortSwigger Web Security Academy

- 参考来源：<https://portswigger.net/web-security/learning-paths>
- 采用内容：围绕明确目标组织学习路径；路径拆分为主题和模块；理论材料与实验相邻；学习进度可恢复。
- ReLum 对应：`路径 -> 阶段 -> 专题模块 -> 章节 -> 靶场`。

### TryHackMe

- 参考来源：<https://help.tryhackme.com/en/articles/8484133-training-content-overview>
- 采用内容：Path、Module、Room、Task 的层级；短任务混排理论和动手内容；Walkthrough 与 Challenge 分工。
- ReLum 对应：专题模块负责系统讲解，章节保持短粒度，靶场承担最终验证。

### Hack The Box Academy

- 参考来源：<https://academy.hackthebox.com/catalogue/paths>
- 采用内容：技能路径与岗位路径分离；模块声明前置知识；课程顺序服务于具体能力产出。
- ReLum 对应：每条路径必须填写受众、前置要求、阶段目标和完成产出，不能只是分类合集。

### OWASP WebGoat 与 Juice Shop

- 参考来源：<https://owasp.org/www-project-webgoat/>、<https://owasp.org/www-project-juice-shop/>
- 采用内容：解释漏洞、动手验证、解释防护的三段式；新手教程按顺序解锁；计分只反映真实挑战结果。
- ReLum 对应：每个章节至少包含原理、判断条件、实验路径、验收和防护复盘。

### OverTheWire

- 参考来源：<https://overthewire.org/wargames/bandit/>
- 采用内容：连续关卡；上一关结果用于下一关；左侧目录始终显示当前位置。
- ReLum 对应：基础与 CTF 路径强调连续章节、可恢复进度和目录定位。

### Hello CTF

- 参考来源：<https://hello-ctf.com/>、<https://github.com/ProbiusOfficial/Hello-CTF>
- 采用内容：零基础引导、信息差补齐、教程与配套题目同源、本地部署优先。
- ReLum 对应：基础路径必须先解释工具、术语和环境，不能默认用户已经掌握安全黑话。

## 3. 固定信息架构

```text
学习路径 Path
  └── 学习阶段 Stage
      └── 专题模块 Module
          └── 知识章节 Section
              └── 本地靶场 Challenge
```

- 路径：围绕一个学习目标或能力方向组织，例如 Web 安全测试。
- 阶段：表示存在前后依赖的一组能力，例如身份、会话与授权。
- 专题模块：一个可独立学习的漏洞或技能专题，例如 SQL 注入。
- 章节：模块中的最小知识单元，例如字符型 SQL 注入。
- 靶场：章节对应的可运行环境，必须通过唯一 flag 验收。

模块可以被多个路径复用，但在不同路径中必须拥有清晰的阶段上下文。

## 4. 当前路径

| 路径 | 目标 |
| --- | --- |
| 安全基础入门 | 建立终端、编码、数据和证据基础 |
| Web 安全测试 | 完成请求分析、漏洞验证、影响判断和修复复测 |
| 组件与漏洞复现 | 完成技术栈识别、版本确认、CVE 复现和报告 |
| CTF 专项能力 | 通过短题和关卡训练问题拆解与工具选择 |
| 蓝队调查与检测 | 完成告警调查、时间线、检测规则和持续调优 |

路径和阶段元数据统一维护在 `src/data/learningPaths.js`。

## 5. 章节编写模板

每个章节应按以下顺序组织：

1. `章节目标`：学习者完成后可以做什么，使用可验证的动词。
2. `核心概念`：解释机制和信任边界，不先给 payload。
3. `触发条件`：漏洞成立所需的输入点、上下文和错误假设。
4. `观察证据`：正常基线、异常响应、日志或流量证据。
5. `最小验证`：使用最小影响操作证明问题存在。
6. `实验步骤`：每一步说明动作、预期现象和失败时的检查点。
7. `验收标准`：必须获得本题 flag；截图或文字答案不能替代。
8. `防护复盘`：根因修复、纵深防御、检测方法和复测步骤。

禁止只堆放命令、payload 或工具截图。示例必须解释使用前提、预期结果和风险边界。

## 6. 难度规则

- 入门：单一知识点，操作路径明确，不需要组合漏洞。
- 中级：需要判断上下文、选择方法或处理一种常见限制。
- 高级：需要组合两个以上知识点、编写辅助脚本或分析复杂证据。
- 专家：需要独立研究版本差异、补丁、协议细节或多阶段攻击链。

难度表示认知和操作复杂度，不应根据文章长度决定。

## 7. 内容验收清单

- 路径中的每个专题都真实存在。
- 每个专题至少属于一条路径。
- 阶段顺序有明确依赖，不按名称随意排列。
- 每个章节都有目标、证据、实验和防护内容。
- 靶场镜像可在受支持平台运行。
- 正确 flag 只能由对应靶场获得，并通过服务端验证。
- 文档示例在当前镜像版本上重新执行过。
- 不在前端源码、课程文本、截图或日志中泄露正确 flag。
